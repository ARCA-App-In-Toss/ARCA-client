# ARCA 프런트엔드 개발 명세 지도

- 문서 버전: v1.16
- 최근 수정일: 2026년 9월 28일
- 상태: 확정
- 승인 주체: 제품 책임자

개발 문서의 관할·선택 읽기·충돌·승인 규칙을 정의합니다. 제품 정책은 [프로젝트 문서 지도 · L1–25](../README.md)와 `docs/`의 SSOT를 따릅니다. 현행 UI 변경과 입력 카운터 표시를 담당 명세에 동기화했습니다. 문구·라우트·서버 계약은 유지합니다.

현행 디자인·입력 기준은 **02의 색/세 크기 타입/모션 → 03의 화면 배치 → 04 IX-001·027의 카운터/목록 표시 → 06 §7.2 구현 → 08 §14.1 검증**으로 연결됩니다. 기록 목록은 OD-23·D-UI-084의 질문·날짜 표시가 이전 응답 발췌 지시를 대체합니다.

## 3. 참조 방향과 중복 방지

- 제품 범위는 [PRD · L1–18](../../docs/ARCA_MVP_PRD.md), 정책은 [Rules · L1–10](../../docs/ARCA_MVP_RULES.md), 화면 전이는 [Flow · L1–12](../../docs/ARCA_USER_FLOW.md), 제품 합격 기준은 [Acceptance · L1–12](../../docs/ARCA_MVP_ACCEPTANCE.md), 제품 결정 상태는 [Open Decisions · L1–25](../../docs/ARCA_OPEN_DECISIONS.md)가 소유합니다.
- 소비 문서는 담당 SSOT를 직접 참조합니다. 결정 이유만 DECISIONS에서 찾고, 역방향 추적 표를 별도 계약으로 해석하지 않습니다. 같은 표·문구·계약을 복사하지 않습니다.
- 읽기 지도는 **파일 경로 + 절/ID + 대략적인 줄 범위**를 제공합니다. 현재 파일의 경로는 머리말에서 한 번만 적고 같은 파일 링크는 절만 표시합니다. 링크 자체는 현재 문서 기준 상대 경로입니다. 본문에서는 짧은 문서명·절/ID를 사용합니다.
- `L…`·`약 L…`는 현재 위치 힌트입니다. 줄이 이동했으면 링크의 제목이나 ID를 해당 파일에서 검색해 주변만 읽습니다. 문서 전체·참조 문서 전체를 기본 입력으로 삼지 않습니다.
- 수정한 절과 이를 가리키는 줄 힌트를 함께 갱신합니다. 원문·수치·문구는 담당 절에만 남기고 인계는 위치와 추가 조건만 적습니다.

## 4. 충돌 우선순위와 정정 절차

같은 책임 범위에서 내용이 충돌하면 다음 순서로 판단합니다.

1. 제품 SSOT
2. `확정` 상태의 담당 개발 명세
3. Mock과 테스트
4. 실제 코드

`DECISIONS`의 요약이나 이전 ID가 담당 명세와 다르면 두 번째 계약으로 적용하지 않습니다. 승인된 결정의 누락·모순이 있는 범위를 확인하고 담당 명세와 결정 안내를 함께 정정합니다.

법령이나 앱인토스 필수 제약처럼 외부의 강제 조건이 새로 확인되면 그것을 제품 정책으로 조용히 대체하지 않습니다. 영향받는 작업을 멈추고 제품 SSOT를 먼저 또는 같은 변경에서 수정·승인한 뒤 개발 명세를 맞춥니다.

충돌을 발견한 사람은 다음 순서로 처리합니다.

1. 충돌한 문장과 ID, 발견 환경, 영향 화면·오퍼레이션을 기록합니다.
2. §2에서 소유 문서를 찾고 영향받는 문서를 `검토 중` 또는 `차단`으로 전환합니다.
3. 제품 결정이면 Open Decisions 절차를, 개발 결정이면 `DECISIONS.md` 절차를 따릅니다.
4. 승인된 결론과 소유 문서, 소비 문서, Mock·테스트, 코드를 같은 변경 단위에서 정정합니다.
5. 링크와 회귀 검증을 통과한 뒤 다시 `확정`합니다.

코드의 현재 동작만으로 제품 의도를 변경하지 않습니다. 비교 프로토타입에서 얻은 사용성·시각 검증 결과는 변경 제안의 근거로 사용하며, 채택 시 소유 문서와 결정 기록에 반영합니다. §7.1의 범위 안에서 진행하는 표현 실험은 운영 명세의 충돌로 취급하지 않습니다.

## 5. 작업 중단 기준

기본 원칙은 **영향 범위만 중단**하는 것입니다. 필수 계약의 미기재·모순·불일치가 있는 화면, 오퍼레이션과 직접 의존 작업을 `차단`하고 독립 작업은 계속합니다. 조정 가능한 기본값과 탐색 가능한 표현은 §7.1의 범위에서 진행하며, 시각 채택 전이라는 이유만으로 독립된 계약·접근성 구현을 차단하지 않습니다.

다음 문제는 공통 기반 또는 핵심 수직 흐름 전체를 차단합니다.

- 응답·닉네임·익명 식별키의 노출, 입력 유실 또는 삭제 누락 가능성
- 익명 식별, 세션 재발급, 탑승 완료 판정의 불일치
- KST 날짜와 저장 가능 여부, 하루 한 응답, 멱등성의 불일치
- 모든 데이터 삭제 범위와 보존 예외의 불일치
- 여러 화면이 공유하는 계약을 안전하게 구분할 수 없는 변경
- 앱이 빌드·시작되지 않거나 실제 토스 환경에서 핵심 흐름을 검증할 수 없는 플랫폼 문제

차단 중에는 가정을 운영 계약이나 되돌리기 어려운 구현으로 고정하지 않습니다. 타입·포트·placeholder처럼 결론을 내포하지 않는 가역적 경계 작업만 진행할 수 있습니다.

## 6. 식별자와 인용 문법

| 대상 | 형식 | 예시 |
|---|---|---|
| 기존 제품 규칙 | 기존 ID 유지 | `ON-05`, `SE-03`, `AN-02` |
| 기존 화면 | 기존 ID 유지 | `F00`, `F11`, `F90` |
| 제품 결정 | 기존 ID 유지 | `OD-06` |
| API 오퍼레이션 | `OP-###` | `OP-001` |
| API 계약 검증 | `API-V-###` | `API-V-001` |
| 공통 컴포넌트 | `CMP-###` | `CMP-001` |
| 상호작용 계약 | `IX-###` | `IX-001` |
| 공통 UI 문구 | `CPY-COM-###` | `CPY-COM-001` |
| 화면 UI 문구 | `CPY-F{화면}-###` | `CPY-F11-018` |
| 디자인 결정 | `D-UI-###` | `D-UI-001` |
| API 계약 결정 | `D-API-###` | `D-API-001` |
| 기술·문서 운영 결정 | `D-TECH-###` | `D-TECH-001` |
| 에셋 | `AST-###` | `AST-001` |

디자인 토큰은 숫자 ID 대신 코드에서 직접 사용할 의미 기반 이름을 씁니다. 예: `color.bg.canvas`, `space.200`. 값이 바뀌어도 의미가 같으면 이름을 유지하고 의미가 달라지면 새 토큰을 만듭니다.

인용에는 문서와 절 또는 ID를 함께 적고 §3의 경로·줄 힌트를 연결합니다. OP·API-V는 05, CMP는 02, IX·CPY는 04, 결정은 DECISIONS, AST는 [Asset Manifest · L1–11](../../design/assets/ASSET_MANIFEST.md)에서 찾습니다.

ID는 의미가 없어지더라도 재사용하지 않습니다. 이름 변경은 같은 ID를 유지하고, 의미·필수 계약의 비호환 변경은 새 ID와 대체 관계를 만듭니다. 컴포넌트의 의미·행동·접근성을 보존하는 시각 기본값 조정이나 호환되는 시각 variant 추가는 같은 CMP ID를 사용합니다. 승인된 개발 결정을 대체할 때는 §8에 따라 새 결정 ID를 남깁니다.

## 7. 문서 상태와 승인

| 상태 | 의미 | 허용되는 사용 |
|---|---|---|
| 초안 | 작성자가 구조와 가설을 채우는 중 | 탐색과 비구속 구현 참고 |
| 검토 중 | 검토 범위가 완성되어 피드백을 받는 중 | 프로토타입 참고, 운영 계약으로 사용 금지 |
| 확정 | 승인 조건을 충족하고 제품 책임자가 승인 | 구현과 QA의 기준 |
| 차단 | 필수 의존성·모순·결정이 해결되지 않음 | 표시된 영향 범위 구현 중단 |
| 폐기 | 대체되었거나 더 이상 사용하지 않음 | 새 문서 링크 확인만 가능 |

기본 전이는 `초안 → 검토 중 → 확정`입니다. 미해결 의존성이 생기면 `차단`, 해결되면 이전 작성 단계로 돌아갑니다. 확정 문서의 필수 계약이나 승인된 방향을 변경할 때는 해당 범위를 먼저 `검토 중`으로 되돌립니다. §7.1에 허용된 실험은 기존 확정본을 유지한 별도 프로토타입에서 진행할 수 있습니다. 폐기 문서에는 대체 문서나 결정 ID를 반드시 남깁니다.

모든 번호 문서 머리말에는 버전·최근 수정일·상태·승인 주체를 기록합니다.

다음 조건을 모두 충족할 때만 `확정`할 수 있습니다.

- 관할 안의 P0 미결정과 차단 항목이 없음
- 제품 SSOT 및 승인된 결정과 충돌하지 않음
- 참조 링크와 ID가 유효함
- 실패·복구·접근성·개인정보 영향이 필요한 문서로 연결됨
- 제품 책임자가 승인함

본문에는 현행 계약·선택 이유·검증 조건만 둡니다. 대화 번호, 리뷰 반영 목록, 문서 작성 완료 체크와 하단 변경 이력을 누적하지 않습니다. 버전·최근 수정일·승인 상태는 머리말에 유지하고, 실제 검증 증거는 `08`, 시각 채택은 [02 §13.3 · L613–629](./02_DESIGN_SYSTEM.md#133-남은-시각-채택-작업)·[03 §10 · L931–957](./03_SCREENS_SPEC.md#10-권장-시작안검증할-결과채택-상태), 에셋 권리는 Asset Manifest에서 관리합니다.

### 7.1 결정 강도와 자율 탐색

문서 상태와 별도로 결정을 다음 세 강도로 구분합니다([D-TECH-024·D-TECH-026 · L88–130](./DECISIONS.md#6-시각-표현과-탐색)). `확정`은 이 구분과 현재 방향·권장 시작안이 승인되었다는 뜻이며, 모든 배치와 시각 값이 실기기에서 검증되었다는 뜻은 아닙니다.

| 강도 | 대상 | 자율 작업과 채택 |
|---|---|---|
| 필수 계약 | 제품 범위·개인정보·저장·삭제·날짜·채택 API 의미/구조·접근성·필수 플랫폼 제약 | 준수하며 구현합니다. 변경은 담당 SSOT와 승인 절차를 거칩니다. |
| 조정 가능한 기본값 | 허용된 방향 안의 색·간격·타입 크기·장식 강도·모션 타이밍, 필수 의미·표시 조건을 지키는 문구 축약·어미 조정 | 필수 계약을 만족하는 범위에서 작성자가 조정·비교할 수 있습니다. 검증 근거와 채택값을 같은 변경에서 토큰·명세에 반영하며 값마다 사전 승인을 요구하지 않습니다. |
| 권장 시작안·탐색 가능한 표현 | 화면의 정보 묶음·배치·행동의 시각적 위계, JOY의 형상·장면 구도·기억 연출·핵심 흐름의 공간 연결, 설명량·문구 배치 | 담당 화면의 검증할 결과를 만족하는 대안을 별도 프로토타입에서 만들 수 있습니다. 비교 결과와 추천안을 제시하고, 채택 시 배치·원본·명세·에셋 기록을 동기화합니다. |

- 문구의 자율 조정은 [04 §7.0 · L576–598](./04_INTERACTIONS_AND_COPY.md#70-필수-의미표시-조건권장-문장)을 따릅니다(D-TECH-028). 중복 설명 삭제·어미 조정에 문장별 사전 승인을 요구하지 않습니다. 채택 문자열과 근거는 같은 변경에서 반영합니다. 저장·삭제 결과, 유실 위험, 복구 제한, 필수 고지·기간, 접근성·행동 의미는 유지합니다.
- 하네스는 현재 채택 문자열과 의미·노출 조건·조작 결과를 함께 검증합니다. 탐색 단계에서 과거 문장과의 문자 일치만으로 의미가 보존된 대안을 배제하지 않습니다.
- API는 [05 §1.2.1 · L36–44](./05_API_SPEC.md#121-계약-강도와-원본)의 제품 불변식·채택 계약·구현 가설로 나눕니다. [05 §16 · L807–819](./05_API_SPEC.md#16-저장-요청-분할-비교와-상태-전이-검증)의 저장 분할 비교는 합성 프로토타입에서 자율 진행할 수 있으며 현재 운영 어댑터 계약을 자동 대체하지 않습니다. 발췌 예산은 04 IX-027에 따라 조정합니다.
- 선별 UI 도입은 D-TECH-050~054의 승인 범위입니다. 02의 디자인/접근성 계약과 04의 동작을 유지하는 컴포넌트별 후보·패키지/소스 편입·스타일 조정은 개별 사전 승인 없이 비교·선택하고 [06 §2.4 · L97–117](./06_FRONTEND_SPEC.md#24-픽셀-ui-선별-도입과-출처-추적)에 출처·수정·검증을 기록합니다. 공통 시각 규칙은 [02 §1.4 · L50–57](./02_DESIGN_SYSTEM.md#14-서로-다른-출처의-시각-통합), 실제 에셋은 Asset Manifest가 소유합니다.
- 소유 문서가 강도·허용 범위·검증 조건을 적습니다. 명시되지 않은 제품·행동·데이터 요구는 필수 계약으로 취급합니다.
- `03`의 위→아래 배치는 권장 시작안이며 화면별로 검증할 결과를 함께 적습니다. 필수 정보·제품 전이·보호 계약·접근성과 승인된 경험 방향을 유지하는 배치 대안은 문서 선행 갱신 없이 비교할 수 있습니다. 정보 누락, 서버 결과 변경이나 새로운 제품 행동은 배치 실험으로 간주하지 않습니다.
- 하네스의 합격 조건은 정보·행동의 발견, 입력 보존, 저장 도달성, 읽기 문맥처럼 관찰 가능한 결과를 우선합니다. 시각 채택 전의 좌표·장면 수·컴포넌트 나열 순서를 유일한 정답으로 고정하지 않으며, 채택한 배치는 원본과 화면 명세에 기록합니다.
- 탐색에는 합성 데이터와 Mock을 사용하며 운영 API·실사용자 데이터에 영향을 주지 않습니다. 미확정 HTTP 경로나 제품 정책을 구현 사실로 고정하지 않습니다.
- 실험용 값·컴포넌트는 프로토타입 내부에 임시임을 표시할 수 있으며, 실험 시작 전에 담당 문서·DECISIONS를 갱신할 의무는 없습니다.
- 채택본은 의미 기반 토큰과 담당 컴포넌트에 통합합니다. 승인 방향을 바꾸는 실험 결과는 새 결정으로 기록하고, 방향 안의 기본값 조정은 담당 명세의 채택값과 검증 근거를 갱신합니다.
- F10 → F11 → F12의 비교 시안과 시각 채택 기준은 [01 §10 · L192–217](./01_UI_OVERVIEW.md#10-에셋과-디자인-원본), 원본·컴포넌트 통합은 [02 §13 · L594–629](./02_DESIGN_SYSTEM.md#13-디자인-원본과-개발-전달)이 소유합니다.

## 8. 개발 결정 기록

- `DECISIONS.md`는 현행 개발 결정의 이유와 담당 명세를 찾는 지도입니다. 제품 결정은 `OD-*`와 제품 SSOT를 참조합니다.
- 결정 ID, 현행 결론, 판단에 필요한 이유와 담당 명세 링크를 남깁니다. 대화 순서·검토 회차·반영 파일 목록은 기록하지 않습니다.
- 결정 변경 시 담당 명세와 소비 문서·검증 조건을 같은 변경에서 갱신합니다. 필수 계약·승인 방향의 변경은 §7의 승인 절차를 따릅니다.
- 의미가 바뀐 결정은 새 ID를 사용합니다. 이전 ID는 재사용하지 않고 현재 결정으로 연결하는 짧은 대체 안내만 남깁니다. 부분 대체는 유지되는 범위를 명시합니다.
- 상세 계약·수치·문구를 결정 기록에 별도 원본으로 복제하지 않습니다. 구현은 §2의 담당 명세를 직접 읽습니다.

## 9. 구현 시작 게이트

작업을 시작하기 전에 다음을 확인합니다.

1. 담당 제품 SSOT와 화면 ID를 확인합니다.
2. 운영 구현은 담당 개발 명세의 필수 계약과 승인 방향이 `확정`인지 확인합니다. 프런트 구조와 실행 순서는 [06 Frontend Spec · L1–27](./06_FRONTEND_SPEC.md)을 적용하고 실제 source·package·하네스가 없다는 상태를 구현 완료로 해석하지 않습니다. 탐색 프로토타입은 §7.1의 범위·가설·비운영 경계를 표시하면 초안·검토 중 문서로도 시작할 수 있습니다.
3. Open Decisions와 `DECISIONS.md`에 차단 결정이 없는지 확인합니다.
4. API 구현은 [05 API Spec · L1–25](./05_API_SPEC.md)의 의미 계약과 [OpenAPI](./arca.openapi.json)의 현재 채택 OP·DTO·HTTP 경로를 따릅니다. 실제 host·백엔드는 아직 없으므로 실서버가 존재한다고 가정하지 않고 도메인 포트와 Mock 어댑터부터 구현합니다.
5. D-TECH-038에 따라 개발용 Mock 승객의 질문→작성→저장→다시 읽기부터 검증하며 운영 동의/탑승 우회는 배포하지 않습니다. 07 시나리오와 08 실기기·실패·접근성 증거를 각 slice에 붙이고 마지막 단계로 미루지 않습니다. 운영 구현은 완료 증거를 남길 `08`의 QA 항목을 연결합니다. 탐색 결과도 제품 Acceptance와 담당 화면의 검증 조건에 연결합니다.
