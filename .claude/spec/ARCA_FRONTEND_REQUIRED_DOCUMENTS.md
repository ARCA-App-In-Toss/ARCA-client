## 참고 프로젝트에서 확인한 패턴

| 영역 | Gravit Admin | Ultimate Sugang | ARCA에 적용할 판단 |
|---|---|---|---|
| 제품·행동 입력 | 와이어프레임 명세 | Behavior Spec | 기존 `MVP_RULES + USER_FLOW`를 재사용 |
| 디자인 입력 | Overview, Design System, Screens, Interactions를 분리 | Design System, Screens로 통합 | 감성 표현과 복구 문구가 많으므로 Overview/System/Screens/Interactions 분리 |
| API 입력 | 경로·메서드·요청·응답·에러가 있는 실제 API Spec | 처음에는 엔드포인트 없이 화면이 요구하는 Operation만 정의 | Operation을 먼저 쓰고 HTTP 계약은 백엔드 합의 후 같은 문서에서 확정 |
| 프런트 계획 | 스택·폴더·인증·횡단정책·Step을 한 문서로 관리 | 어댑터 경계와 mock-first Step을 같은 문서로 관리 | Frontend Spec 한 문서로 관리 |
| Mock | 개발 환경에서 MSW가 확정된 HTTP 요청을 가로챔 | 도메인 `Api` 인터페이스 뒤 `mock`/`http` 어댑터 전환 | 계약 미확정인 ARCA는 어댑터 방식 우선 |
| 실 API | feature API가 axios client를 사용하고 응답을 Zod로 검증 | 서버 envelope·필드·에러를 `httpAdapter`에서 화면 모델로 변환 | 화면을 바꾸지 않고 HTTP 어댑터에서 차이 흡수 |
| 구현 단위 | 단순 화면 → CRUD → 복잡 화면 → QA | 셋업 → 인프라 → 화면 그룹 → QA | 최초 탑승과 첫 저장을 첫 수직 흐름으로, 이후 화면 단위 진행 |
| 완료 확인 | 화면별 4상태, 상호작용, 타입·빌드, 스모크, 리뷰 | 같은 구조 + Mock 실패·경계 시나리오 | QA 문서에 동일한 완료 증거 정의 |

두 프로젝트 모두 한 화면을 `스키마 → API → 쿼리/뮤테이션 훅 → 컴포넌트 → 얇은 페이지 → 라우트` 순서로 연결했다. Figma는 있으면 시각 참고로 사용했지만 필드·동작·API·검증의 권위로 사용하지 않았고, 화면마다 Loading/Error/Empty/Data 및 성공·실패·복구를 확인했다.

여기서 말하는 퍼블리싱은 화면 구현에 해당한다. 두 `.claude` 하네스 모두 실제 배포, 비밀값 입력, 외부 publish 같은 작업은 사람에게 위임했으므로 별도 배포 문서의 근거로 보지는 않는다.

## 1. 결론

ARCA의 제품 기획 문서는 이미 구현 인테이크로 쓸 수 있을 만큼 잘 분리되어 있다. 따라서 PRD나 사용자 흐름을 다시 쓰지 말고, 아래 **번호 문서 9종(`00`~`08`)과 보조 결정 기록 1종**을 준비하는 것이 적절하다. 우선 작성 범위는 번호 문서 9종이다.

## 3. 문서별 결정 인벤토리와 최소 포함 항목

이 절은 `00`~`08` 문서를 작성할 때 사용할 인테이크다. 각 문서의 항목은 다음 기준으로 나눈다.

- **결정된 내용**: 현재 제품 SSOT 또는 플랫폼 선정안에서 이미 확정된 사실이다. 새 문서에서는 결론을 다시 만들지 않고 원문 링크와 ID를 인용해 구현 가능한 수준으로 구체화한다. 요약과 원문이 충돌하면 원문을 따른다.
- **결정해야 할 내용**: 현재 문서만으로 하나의 구현을 선택할 수 없는 사항이다. 앞으로 문서별 대화에서 선택지·근거·영향 범위를 검토한 뒤 확정한다.
- 이미 닫힌 `OD-01`~`OD-10`과 PRD의 MVP 제외 항목은 열린 질문으로 되돌리지 않는다. 제품 정책을 바꿔야 할 때만 `ARCA_OPEN_DECISIONS`를 다시 연다.
- 하나의 항목 안에 확정 정책과 미정 구현 방식이 함께 있으면 둘을 분리한다. 예를 들어 `임시본 7일 보존`은 결정됐지만 저장소 종류와 key 형식은 결정해야 한다.

### 3.1 `00_INDEX.md` — 개발 문서 지도

#### 결정된 내용

- 제품 문서의 책임과 읽기 순서는 [프로젝트 문서 지도](../README.md)에 정의되어 있다. 제품 범위는 PRD, 공통 정책은 Rules, 화면 상태·전이는 User Flow, 검증 기준은 Acceptance, 열린 제품 결정은 Open Decisions가 담당한다.
- 한 결정은 한 SSOT에만 기록하고 다른 문서는 링크나 ID로 참조한다. 제품 결정이 바뀌면 제품 SSOT를 먼저 또는 같은 변경에서 갱신한다.
- `00`~`08`의 문서 목적과 우선순위는 이 문서 §1의 표를 기준으로 시작한다.
- 현재 추적 가능한 식별자는 규칙 ID(`ON/SE/AN/AR/CS/DP-*`), 화면 ID(`F00`~`F90`), Acceptance 번호(`#1`~`#33`), 닫힌 제품 결정 ID(`OD-01`~`OD-11`)다.
- API 계약, UI 상세와 프런트엔드 아키텍처는 기존 제품 문서의 책임이 아니며 새 개발 문서에서 정의한다.

#### 결정해야 할 내용

- `00`~`08` 각각이 최종 권위를 갖는 정확한 범위와, Screen·Interaction·API처럼 경계가 맞닿는 문서 사이의 참조 방향
- 제품 SSOT, 개발 명세, 승인된 결정 기록, 코드가 충돌할 때의 우선순위와 정정 절차
- 미기재·모순·계약 불일치를 발견했을 때 전체 구현 또는 해당 화면·오퍼레이션만 멈출지 판단하는 기준
- 오퍼레이션 ID, 디자인 토큰/컴포넌트 ID, 기술·디자인 결정 ID의 체계와 기존 ID를 인용하는 문법
- 문서 상태(`초안/검토 중/확정/차단/폐기` 등), 상태 전이 조건, 승인 주체와 변경 이력 형식
- 보조 `DECISIONS.md`에서 제품 결정과 개발 결정을 나누는 기준, 결정 ID·근거·대안·영향 범위·변경/폐기 관계를 기록하는 방식

이 문서가 없으면 화면·디자인·API 문서에 같은 결정을 반복 기록하게 된다.

### 3.2 `01_UI_OVERVIEW.md` — 디자인 인테이크 개요

#### 결정된 내용

- 제품 정의, 1차 사용자, 주요 이용 상황과 핵심 가치는 [PRD](../../docs/ARCA_MVP_PRD.md) §1~§7을 따른다.
- 대상은 토스 앱 안에서 실행되는 앱인토스 비게임 미니앱이며, iOS·Android 실제 토스 앱을 모두 검증한다.
- 기본 실행 환경은 WebView SDK와 Granite이며, 필수 플랫폼 Navigation·플로팅 탭 규격, Safe Area와 네트워크 상태 확인을 P0 기능으로 사용한다([플랫폼 선정안](../../spec/platform/ARCA_APPS_IN_TOSS_FEATURES.md) §2).
- 앱 소유 UI는 픽셀 브랜드 문법 안에서 역할별 서체·장식 위계를 사용하며 한 화면에 하나의 주요 행동을 둔다(PRD §7, [D-UI-032·D-UI-034](./DECISIONS.md)).
- 최상위 IA는 하단 `오늘`·`기록` 두 탭과 상단 `설정` 진입으로 구성한다([User Flow](../../docs/ARCA_USER_FLOW.md) §1).
- 화면 범위는 `F00`, `F01`, `F02`, `F03`, `F10`~`F13`, `F20`~`F23`, `F30`, `F31`, `F90`이다(User Flow §2).
- 섹션은 내부에서만 배정하고 MVP 화면에는 노출하지 않는다(`OD-07`, `ON-04`). 성별·연령·프로필 이미지도 화면에서 다루지 않는다.
- 원본 콘텐츠는 [인트로 서사](../../docs/ARCA_INTRO_STORY.txt), 그래픽·폰트의 확보·권리·시각 채택 상태는 [Asset Manifest](../../design/assets/ASSET_MANIFEST.md)에서 확인한다.

#### 결정해야 할 내용

- `조용하고 절제된 SF`를 포함한 구체적인 비주얼 키워드, 감정 곡선, 금지할 시각 표현과 대표 레퍼런스
- 최소 지원 화면 폭, 콘텐츠 최대 폭, 가로 여백, 세로 스크롤과 작은 화면 대응의 전역 원칙
- Safe Area, 소프트 키보드, Android 시스템 뒤로가기와 앱인토스 내비게이션을 레이아웃 차원에서 처리하는 원칙
- 하단 탭과 설정 진입 버튼을 각 화면에서 언제 표시·숨김·대체할지
- 라이트 모드만 제공할지, 다크 모드를 지원할지, 토스 앱의 테마 설정을 따를지
- 세계관 날짜를 보조 정보로 실제 사용할지(`SE-03`은 허용만 하며 사용을 확정하지 않음)
- 로고·픽셀아트·아이콘·일러스트·모션·사운드별 필요 목록, 현재 확보 상태, 원본 위치와 라이선스
- 앱인토스가 강제하는 플랫폼 UI와 ARCA 픽셀 앱 소유 영역의 시각적 경계 및 Figma 등 디자인 원본의 생성·소유 위치

Gravit의 `DS-00_overview`처럼 화면을 그리기 전에 디자인 도구와 개발자가 같은 맥락을 갖게 하는 문서다.

### 3.3 `02_DESIGN_SYSTEM.md` — 디자인 시스템

#### 결정된 내용

- 플랫폼과 ARCA 구현 경계는 [01 §4](./01_UI_OVERVIEW.md), 현재 디자인 방향·계약·기본값·탐색 범위는 [02 §2.3](./02_DESIGN_SYSTEM.md)을 따른다.
- 서체·명도·장식·질문·작성·JOY·기록편·목록·장면 변경은 [D-UI-032~D-UI-040](./DECISIONS.md)에 기록되어 있다. 전면 단일 서체·밝은 입력·중앙 crop 등 대체된 해법을 다시 구현 기준으로 사용하지 않는다.
- 기본값 조정과 비운영 표현 실험은 [00 §7.1](./00_INDEX.md)에 따라 자율 진행하고, 시각 채택은 [01 §10](./01_UI_OVERVIEW.md)의 비교 시안·기준 원본·증거로 마무리한다.
- 저장·비공개·접근성·건너뛰기·최대 2초·Reduced Motion 등 필수 계약은 담당 제품·디자인 명세를 따른다.

#### 확정된 최소 포함 항목

아래 인테이크의 현재 승인 방향과 남은 시각 채택 범위는 [Design System](./02_DESIGN_SYSTEM.md)과 [개발 결정 기록](./DECISIONS.md)을 따릅니다. 최초 수치·형상을 모두 고정한 목록으로 사용하지 않습니다.

- ARCA 픽셀 컴포넌트의 전체 목록과 앱인토스 필수 플랫폼 UI 예외, headless primitive가 맡는 동작 경계
- 색상, 타이포그래피, 간격, 크기, 모서리, 테두리, 그림자, 투명도, 레이어와 모션 토큰
- Safe Area·작은 화면·큰 글자에 대응하는 레이아웃 토큰과 브레이크포인트
- Button, Textarea, 의미별 Surface, Dialog, Sheet, Toast, Navigation 등 공통 컴포넌트의 이름·상태·조합 규칙
- Default/Hover/Pressed/Focus/Disabled/Loading/Error/Read-only 상태 중 컴포넌트별 적용 범위와 시각·의미 표현
- SEMA, JOY, 기억 조각, 누적 개수, 항해 기록을 서로 구분하는 시각 문법
- 픽셀아트의 기준 해상도, 정수 배율, 보간 방식, 포맷·용량 예산, 반응형 크롭과 대체 이미지 원칙
- 기억 조각 연출의 장면·전환·건너뛰기 입력, `prefers-reduced-motion` 대체안과 햅틱 채택 여부
- 색 대비, 동적 글자 크기, 포커스 표시·순서, 터치 타깃, 스크린 리더 이름과 상태 알림의 구체 기준
- 라이트/다크 모드 결정에 따른 토큰 구조와 디자인 파일 수치를 코드 토큰으로 매핑하는 방식

운영 채택값은 Design System의 토큰에 매핑한다. 별도 프로토타입의 임시 값은 00 §7.1의 탐색 범위를 따른다.

### 3.4 `03_SCREENS_SPEC.md` — 화면별 명세

#### 결정된 내용

- 화면 ID, 이름, 핵심 진입 조건·행동·성공/실패 전이는 [User Flow](../../docs/ARCA_USER_FLOW.md) §2~§8에 정의되어 있다.
- F00은 익명 식별키·승객·온보딩·서버 날짜·오늘 응답 상태를 조회해 F01/F10/F90으로 분기하며, 조회만으로 승객을 만들지 않는다.
- F01~F03은 건너뛸 수 있는 인트로, 필수 약관 동의 뒤 승객 생성, 선택형 닉네임과 승객 코드 확인 순서다. 인트로 장면 수는 아직 확정되지 않았다.
- F10~F13은 기본/대체 질문 선택, 질문별 임시본, 명시적 저장, 최초 저장 연출, 저장 전 날짜 변경과 내용 복사를 다룬다.
- F20~F23은 자기 응답 원문 발췌 중심의 최신순 20개 단위 목록, 빈 상태, 전문 상세, 수정·발췌 갱신과 1회 확인 후 개별 삭제를 다룬다(`AR-01`, `AR-09`, `OD-11`).
- F30~F31은 승객 정보·정책·고객센터·닉네임 변경과 2단계 전체 삭제를 다루며, F90은 시작 실패의 재시도와 고객센터 연결을 제공한다.
- 화면에 필요한 개념 필드와 제품 상태는 Rules §8, 화면별 표시 필드는 User Flow에 정의되어 있다. 저장 당시 질문 식별자·버전·원문 스냅샷을 상세에 사용한다(`SE-09`).
- 로딩 실패, 저장 중/성공/실패, 기록 없음, 추가 목록 실패, 세션 만료, 날짜 변경, 장기 점검과 네트워크 단절의 결과는 User Flow에 정의되어 있다.
- 화면과 주요 행동에 대응하는 제품 분석 이벤트 13개와 금지 속성은 [Acceptance](../../docs/ARCA_MVP_ACCEPTANCE.md) §1에 정의되어 있다.
- 질문 확인·변경·입력의 큰 글자/스크린 리더 접근성, iOS 키보드, Android 뒤로가기 검증은 Acceptance #26~#28의 필수 조건이다.

#### 결정해야 할 내용

- 모든 화면에 공통으로 적용할 명세 템플릿: ID·목적·진입/이탈·주/보조 행동·필드/출처·레이아웃·상태·접근성·추적 ID
- F00~F90 각각의 위→아래 레이아웃, 정보 위계, 고정/스크롤 영역과 사용 컴포넌트·토큰
- 각 표시 필드를 어떤 API 오퍼레이션·로컬 상태에서 가져오며, 로딩 전·부분 응답·오래된 캐시에서 무엇을 보여줄지
- 화면별 Loading/Error/Empty/Data/Disabled/Read-only/제출 중/충돌 상태와 해당 없음의 근거
- F01의 장면 수·스토리보드·진행 표시·건너뛰기 뒤 핵심 메시지, F10의 SEMA 문장과 질문 배치, F12의 연출 장면
- F13에서 보존된 지난 임시본을 다시 열람·복사하는 진입 경로와 만료 표시 방식
- F30의 닉네임 수정, 정책 전문, 고객센터 진입을 같은 화면·하위 화면·외부 화면 중 무엇으로 표현할지
- 각 화면의 앱바·하단 탭·뒤로가기, 키보드 회피, 초기 포커스·복귀 포커스, 읽기 순서와 Safe Area 상세
- 분석 이벤트를 화면 상태와 사용자 행동에 정확히 매핑하는 시점, 허용 속성과 중복 방지 조건
- 화면별 연결 Rules/Flow/API/Decision ID 및 디자인 원본 프레임을 기록하는 방식

정상 화면 한 장만 그리지 말고 날짜 변경, 저장 실패, 기록 0건, 점검, 전체 삭제 실패 같은 상태를 같은 화면 명세 안에 포함한다. User Flow에 따옴표로 적힌 행동명은 동작을 식별하기 위한 표현이며 최종 UI 문구는 `04`에서 확정한다.

### 3.5 `04_INTERACTIONS_AND_COPY.md` — 상호작용·문구 카탈로그

#### 결정된 내용

- 인트로는 모든 장면에서 건너뛸 수 있고, 사용자는 질문·응답·기록 어느 단계에서도 답하지 않고 떠날 수 있다(`ON-01`, PRD §7).
- 필수 약관을 모두 동의하기 전에는 탑승 행동을 실행할 수 없으며, 승객 생성 실패 시 동의 상태를 유지한다(F02).
- 닉네임은 선택값이고 2~12자 규칙을 따르며, 건너뛰어도 진행할 수 있다(`ON-05`).
- 유효한 응답은 1~2,000자이고, 저장 중 중복 실행을 막으며, 실패 시 입력을 유지하고 재시도할 수 있어야 한다(`AN-01`~`AN-05`).
- 질문을 바꾸거나 화면을 나가거나 앱이 종료되어도 질문별 임시본 정책을 지키며, 날짜가 바뀐 과거 신규 응답은 저장하지 않고 내용 복사를 제공한다.
- 세션 만료 시 재발급 뒤 한 번 자동 재시도하고, 재실패 시 입력을 유지한다(User Flow F11 저장 결과).
- 개별 삭제는 대상 확인 1회 후 실행하고 되돌리기를 제공하지 않는다. 전체 삭제는 범위·비가역성·보존 예외를 알린 뒤 2단계로 확인한다(`AR-04`~`AR-08`).
- 뒤로가기는 확인 화면→원래 화면, 기록 상세→목록, 설정→이전 화면의 순서를 따르고, 작성 화면에서는 임시 저장 처리 뒤 이탈한다(User Flow §8).
- 문구는 답변을 평가·진단하거나 죄책감·연속 출석 압박을 만들면 안 되며, 응답 본문·닉네임·익명 식별키 원문을 오류 문구나 식별 코드에 노출하면 안 된다.
- 고객 문의는 설정과 시작 오류에서 동일한 앱인토스 고객센터로 연결하고 별도 이메일을 표시하지 않는다(`CS-01`).

#### 결정해야 할 내용

- 탭, 버튼, 텍스트 링크, 스와이프, 키보드 제출 등 지원할 입력 방식과 중복·연속 입력 처리
- Dialog, Bottom Sheet, Toast, Snackbar, 인라인 오류, 전체 화면 오류를 선택하는 기준과 동시에 발생했을 때의 우선순위
- 닉네임·응답의 검증 시점, 글자 수 계산·표시, 오류 노출·제거 시점과 포커스 이동
- 자동 임시 저장의 사용자 피드백, 저장 실패/유실 가능성 경고가 필요한 조건, 이탈 확인을 띄울 정확한 기준
- 서버 저장 중 잠금 범위, 타임아웃 뒤 상태, 수동 재시도와 자동 재시도의 표시 방식
- Android 시스템 뒤로가기, 화면 내 뒤로가기, 하단 탭, 외부 정책·고객센터 화면 복귀가 겹칠 때의 우선순위
- 최초 저장 연출 건너뛰기, 복사 성공/실패, 질문 전환, 추가 페이지 로딩의 세부 피드백
- 성공, 오류, 빈 상태, 점검, 오프라인, 세션 만료, 날짜 변경, 만료된 임시본, 삭제의 정확한 한국어 문구
- 개별 삭제와 전체 삭제의 제목·본문·버튼 순서, 위험 행동 색상과 스크린 리더 알림
- 세계관 용어를 처음 설명하는 위치와 일반어를 병기하는 방식, 존댓말·문장부호·숫자·날짜 표기 규칙

Gravit은 별도 Interaction 문서를, Ultimate Sugang은 Behavior/Screen 문서 안의 메시지 카탈로그를 사용했다. ARCA는 오류·복구 상태와 감성 문구가 많으므로 별도 문서가 안전하다.

### 3.6 `05_API_SPEC.md` — API 계약

이 문서는 제품 계약을 먼저 고정한 뒤 HTTP 계약을 채우는 두 단계로 작성한다.

#### 결정된 내용

- 프런트엔드는 시작 상태 조회, 필수 동의와 승객 생성, 닉네임 변경, 오늘의 SEMA 조회, 응답 생성·조회·수정·개별 삭제, 기록 목록·상세, 모든 데이터 삭제를 수행할 수 있어야 한다. 화면 범위 밖의 운영자 API는 이 문서의 대상이 아니다.
- 동일한 앱인토스 익명 식별키에는 기존 승객과 기록을 연결하고, 식별키가 바뀌거나 없으면 수동 복구하지 않는다(`ON-08`). 익명 식별키를 ARCA 세션으로 교환하는 방식은 아직 미정이다.
- 프런트 도메인에 필요한 승객·SEMA·질문·응답·임시본·동의의 개념 상태와 필드 의미는 Rules §8에 정의되어 있다.
- 날짜는 KST로 구분하고 저장 가능 여부는 ARCA 서버가 최종 판정한다. 과거 미작성 SEMA의 신규 저장은 거절하되 과거 저장 응답의 수정·삭제는 허용한다(`SE-01`, `SE-05`).
- 한 승객·SEMA에는 선택 질문과 무관하게 활성 응답이 최대 1개이며, 반복 저장으로 새 응답을 만들지 않는다(`SE-06`, `AN-03`).
- 저장한 응답에는 선택 질문의 식별자·버전·원문 스냅샷, 생성·마지막 수정 시각과 수정 여부가 필요하다(`SE-09`, `AN-07`).
- 응답은 1~2,000자, 닉네임은 정규화 후 보이는 문자 2~12자라는 서버 검증 규칙을 따른다(`AN-01`, `ON-05`).
- 기록은 최신순 최대 20개씩 원문 발췌를 함께 제공하고 추가 페이지 실패 시 기존 목록을 유지한다. 수정 성공 시 발췌를 갱신하고 삭제 성공 시 목록에서 제거한다(`AR-01`, `AR-09`, F20). 목록 표시를 위해 행마다 상세를 추가 호출하는 구조에 의존하지 않는다.
- 세션 만료, 날짜 변경, SEMA 운영 중지, 중복 요청, 네트워크·서버 실패와 삭제 실패를 프런트가 구분해 정해진 복구 행동을 제공할 수 있어야 한다.
- 전체 삭제의 대상, 즉시 삭제, 최소 동의 증빙 1년 보존과 백업 30일 만료 정책은 `AR-05`~`AR-08`을 따른다.
- 통신은 HTTPS를 사용하고 응답 본문·닉네임·익명 식별키 원문을 로그·분석·오류 추적에 남기지 않는다(`DP-01`~`DP-07`).

#### 결정해야 할 내용 — Mock 시작 전

- 화면 기능을 어떤 오퍼레이션으로 나눌지, `OP-*` ID·이름·입력·출력·부작용과 화면 매핑
- 프런트 도메인 모델의 정확한 타입, enum 값, nullable/optional 구분과 허용 상태 전이
- 제품 오류를 어떤 프런트 오류 종류로 정규화하고 각 오류에 어떤 복구 가능성·사용자 행동을 부여할지
- 목록의 발췌·생략 여부 필드와 원문 일치·길이 계약, 커서 형식·다음 페이지·정렬 안정성 및 삭제·수정 후 발췌/목록 일관성
- KST 날짜·서버 시각·클라이언트 표시 시각의 형식과 23:59→00:01 경계에서 요청을 판정하는 계약
- 생성/저장 멱등성을 보장하는 키와 재요청 규칙, 동시 저장·수정·삭제 충돌 시 승자와 응답 형태
- SEMA·질문·응답 스냅샷을 도메인 응답에 어느 범위까지 포함하고 어떤 화면에서 재조회할지

#### 결정해야 할 내용 — 백엔드와 합의

- API 버전, Base URL, 경로, HTTP 메서드와 환경별 호스트
- 앱인토스 익명 식별키 전달·검증, ARCA 세션 발급/갱신/만료, 인증 헤더와 로그아웃·전체 삭제 뒤 처리
- 요청·응답 JSON 예시, 날짜·시각 인코딩, nullable 여부, 성공 상태 코드와 빈 body 허용 여부
- 공통 error envelope, 도메인 error code, 사용자에게 노출하지 않을 내부 오류 정보와 안전한 오류 식별자
- timeout, 취소, CORS, 네트워크 재시도와 세션 만료 시 한 번 자동 재시도할 수 있는 요청의 범위
- 약관 종류·버전·동의 시각의 전송 형식과 승객 생성 부분 실패 방지, 전체 삭제 완료·부분 실패를 표현하는 방식
- 계약 변경·하위 호환·enum 추가 정책과 Mock/실서버 계약 검증 방법

계약이 오기 전에는 엔드포인트를 지어내지 말고 오퍼레이션 계약부터 정의한다.

### 3.7 `06_FRONTEND_SPEC.md` — 프런트엔드 구조와 구현 계획

#### 결정된 내용

- 정상 화면만이 아니라 실패·복구와 실제 iOS/Android 토스 앱 동작까지 구현 완료 범위에 포함한다.

#### 결정해야 할 내용

- 실제 프런트엔드 저장소 위치, 공식 일반 `react-ts` 템플릿 기준, TypeScript·Granite·React·Emotion·headless primitive의 버전 고정 위치와 업데이트 정책

- 라우트 구조와 앱인토스 최초 진입·백그라운드 복귀·딥링크·외부 화면 복귀·세션 재수립 처리

## 5. 같은 방식으로 구현하는 작업 순서

### 5.1 문서 준비

1. 기존 제품 문서를 읽고 화면·도메인·API·상태전이·검증·디자인·비가역 작업 축으로 커버리지 표를 만든다.
2. 빠진 내용을 추측하지 않고 제품 질문은 OD, 기술 결정은 Decision 후보로 분리한다.
3. `00_INDEX`에서 각 사실의 담당 문서를 하나만 정한다.
4. P0 문서의 최소 필드가 찼는지 확인한 뒤 구현을 시작한다.

### 5.2 화면 퍼블리싱 루프

```text
대상 화면 1개 선택
→ Rules/Flow + UI Overview + Design System + Screen + Interaction 읽기
→ 화면의 상태와 완료 조건 고정
→ 공통 컴포넌트/토큰으로 정적 화면 작성
→ Loading/Error/Empty/Data와 입력·실패·복구 추가
→ 접근성·실기기·시각 대조
→ 차이와 결정을 기록
→ 다음 화면
```

Figma가 있으면 레이아웃과 시각 의도의 참조로 사용하되, 필드·동작·API·검증은 제품/API 문서가 우선한다. Figma 수치를 그대로 코드에 넣지 않고 Design System 토큰으로 매핑한다.

### 5.3 Mock 우선 루프

```text
Screen/Flow에서 필요한 OP 정의
→ 도메인 API 인터페이스 정의
→ 런타임 스키마 정의
→ fixture + 정상/실패/경계 시나리오 구현
→ 화면은 공개 API 인터페이스만 호출
→ Mock E2E 통과
```

ARCA 권장 구조는 다음과 같다.

```text
화면/훅 → arcaApi(검증된 도메인 결과)
                  ├─ mockAdapter
                  └─ httpAdapter
```

Mock도 스키마 검증을 통과시켜 fixture 오염을 조기에 잡는다. 시계·실패·세션은 이름 있는 시나리오로 주입하며, 실제 사용자 데이터를 fixture로 복사하지 않는다.

### 5.4 실 API 연동 루프

1. Mock으로 검증된 도메인 인터페이스와 백엔드 HTTP 계약을 대조한다.
2. 서버의 envelope, 필드명, 날짜 형식, 에러 코드를 `httpAdapter`에서 도메인 모델로 변환한다.
3. 화면·훅·컴포넌트는 변경하지 않는다. 변경이 필요하면 먼저 API 포트나 Screen Spec이 틀렸는지 확인한다.
4. Mock과 실서버에 동일한 핵심 시나리오를 실행한다.
5. 스키마 불일치와 서버 고유 오류를 숨기지 않고 계약 이슈로 기록한다.
6. 실 API 연동 후에도 Mock을 로컬 개발과 회귀 테스트용으로 유지한다.

HTTP 계약이 백엔드에서 먼저 완전히 확정되는 경우에는 Gravit처럼 MSW로 실제 요청을 가로채는 방식도 가능하다. ARCA 초기 단계에서는 계약 미확정이므로 어댑터 방식이 더 적합하다.

### 5.5 검토 루프

화면 또는 작은 수직 흐름이 끝날 때마다 다음을 남긴다.

- 이번 범위와 변경 파일
- 충족한 규칙·화면·API ID
- 디자인 원본과 다른 부분 및 이유
- lint/typecheck/build/test 결과
- 정상·실패·복구 상태 확인 결과
- 미해결 질문과 다음 구현 단위

하네스 리뷰 패킷 파일 자체는 필요하지 않지만, 위 정보는 PR 설명이나 작업 기록의 완료 증거로 유지해야 한다.

## 6. 참고 프로젝트에서 그대로 가져오면 안 되는 것

- Gravit의 데스크탑 1280px 고정 레이아웃: ARCA는 모바일 WebView다.
- Gravit의 관리자 JWT/OAuth 정책: ARCA는 앱인토스 익명 키와 자체 세션 계약이 필요하다.
- Gravit의 MSW 기본 구조: ARCA는 아직 HTTP 계약이 없으므로 도메인 어댑터가 우선이다.
- Ultimate Sugang의 대학 사이트 재현용 CSS·메시지·네이티브 alert 정책: ARCA는 전용 픽셀 컴포넌트와 자체 접근성·문구 기준을 사용한다.
- 두 프로젝트의 React/Vite/라이브러리 버전: 실제 ARCA 프런트 저장소 생성 시 공식 앱인토스 템플릿과 호환성을 다시 확인한다.
- `.claude`의 배포/publish 자동 실행: 두 참고 하네스 모두 실제 배포·비밀값 입력·비가역 작업을 사람에게 위임했다. 여기서 확인되는 것은 화면 구현과 검증 방식이며, 실제 배포 절차의 근거는 아니다.

## 7. 문서 작성에서 먼저 다룰 결정 순서

현재 `ARCA_OPEN_DECISIONS`에 열린 MVP 제품 결정은 없다. `OD-01`~`OD-11`은 모두 닫혔으며, 섹션은 MVP 화면에 노출하지 않는 것으로 확정됐다. 따라서 이미 정한 제품 정책을 다시 묻지 않고, 각 문서를 작성하면서 다음 순서로 디자인·계약·기술 결정을 내린다.

1. `00_INDEX`: 문서별 관할, 충돌·멈춤 규칙, ID·상태·승인 방식
2. `01_UI_OVERVIEW`: 디자인 원본 위치, 비주얼 방향, 에셋 현황, 화면 폭·테마·전역 레이아웃
3. `02_DESIGN_SYSTEM`: 플랫폼/앱 소유 경계, 픽셀 토큰·컴포넌트·폰트·에셋·모션·접근성 기준
4. `03_SCREENS_SPEC`와 `04_INTERACTIONS_AND_COPY`: 화면별 레이아웃·상태와 최종 행동·문구
5. `05_API_SPEC`: 오퍼레이션·도메인 오류를 먼저 정하고, 익명 키-세션 교환과 HTTP 계약을 백엔드와 합의
6. `06_FRONTEND_SPEC`: 저장소 위치·스택 버전·상태 소유권과 Mock-first API 포트/어댑터 채택 여부
7. `07_MOCK_SCENARIOS`와 `08_QA_AND_INTEGRATION`: 결정적 시나리오 주입 방식, 계약·E2E·실기기 게이트와 증거 형식

기본값 조정·표현 탐색은 00 §7.1을 따르며 승인된 방향을 반복 질의하지 않습니다.

이 순서는 최초 작성 계획의 기록입니다. 실제 완료 상태와 다음 작성 대상은 [개발 명세 지도](./00_INDEX.md)를 따르며, 각 문서를 확정할 때 §3의 `결정된 내용`은 원문 ID로 인용하고 아직 닫히지 않은 항목만 사용자와 새로 합의합니다.
