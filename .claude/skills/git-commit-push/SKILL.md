# Git 커밋 & 푸시

변경사항을 사용자의 커밋 컨벤션에 따라 스테이징, 커밋, 푸시하는 스킬입니다. 사용자는 **간결한** 커밋 메시지와 고정된 커밋 타입을 원하며, 형식은 항상 `<type>: <subject>`입니다.

## 커밋 컨벤션

### 허용 타입

| 타입      | 사용 대상                      |
| ------- | -------------------------- |
| `feat`  | 새로운 기능 또는 동작 추가            |
| `fix`   | 버그 수정                      |
| `docs`  | 문서 변경만 있는 경우               |
| `chore` | 빌드, 설정, 의존성, 도구, 비코드성 유지보수 |
| `test`  | 테스트 추가 또는 수정               |

위 목록 외 타입은 사용하지 않습니다 (`refactor`, `style`, `perf`, `ci` 등 금지).

변경이 다섯 타입 중 하나로 명확히 매핑되지 않으면 추측하지 말고 사용자에게 어떤 타입을 사용할지 물어봅니다.

### 메시지 형식

항상 다음 형식만 사용합니다.

```text
<type>: <subject>
```

예시:

```text
feat: 알림 엔티티 추가

feat: 초기 프로젝트 설정

fix: 스케줄러 중복 실행 방지

docs: README 설치 절차 보강

chore: 의존성 버전 업데이트

test: 알림 발송 단위 테스트 추가
```

### Subject 작성 규칙

* **간결하게 작성합니다.**
* 변경 내용을 한눈에 알 수 있는 짧은 요약으로 작성합니다.
* 마침표로 끝내지 않습니다.
* 설명문이 아닌 압축된 구문을 사용합니다.
* 불필요한 수식어를 넣지 않습니다.
* `scope`를 사용하지 않습니다.
* `feat(step-1-setup): ...`과 같은 형태를 사용하지 않습니다.
* `<type>` 뒤에는 항상 `:`만 사용합니다.
* subject 안에서 여러 변경 사항을 구분해야 할 경우 `-` 또는 `,`를 사용합니다.
* 긴 대시(`—`, `–`)는 사용하지 않습니다.
* 가운데점(`·`)은 사용하지 않습니다.
* 변경 사항이 하나라면 불필요하게 `-`나 `,`를 사용하지 않습니다.

예시:

```text
feat: 초기 프로젝트 설정

feat: 로그인 API 추가

feat: 로그인 API 추가 - 토큰 발급 및 검증

fix: 수강신청 중복 등록 방지

fix: 장바구니 삭제 오류, 응답 상태 코드 수정

docs: API 명세 보강 - 세션 생성 및 주제 조회

chore: 테스트 환경 설정 변경 - Redis 포트 수정

test: 수강신청 동시성 테스트 추가
```

### 커밋 단위

* 커밋 하나당 하나의 논리적 변경을 원칙으로 합니다.
* 서로 무관한 변경이 섞여 있으면 하나의 혼합 커밋으로 만들지 않고 분리를 제안합니다.
* 단, 서로 밀접하게 연관되어 하나의 작업으로 보는 것이 자연스러운 변경은 하나의 커밋으로 처리할 수 있습니다.

## 작업 흐름

아래 순서를 따릅니다. 검토 단계를 건너뛰지 않습니다.

### 1. 현재 상태 확인

다음을 순서대로 실행합니다.

```bash
git status
git diff --stat
git diff
```

스테이징된 변경과 미스테이징 변경을 모두 확인합니다.

커밋할 변경이 없으면 중단하고 사용자에게 알립니다.

### 2. 타입 및 메시지 결정

* 실제 diff를 읽고 올바른 타입을 결정합니다.
* 파일명만으로 타입을 추론하지 않습니다.
* 변경 목적과 실제 코드 변경 내용을 기준으로 판단합니다.
* 서로 무관한 변경이 섞여 있으면 이를 알리고 커밋 분리를 제안합니다.
* 커밋 메시지는 반드시 `<type>: <subject>` 형식을 사용합니다.
* 타입이 명확하지 않으면 추측하지 말고 사용자에게 확인합니다.
* 저장소의 기존 커밋 메시지 언어를 확인하여 subject 언어를 결정합니다.
* 기존 컨벤션이 한국어면 한국어, 영어면 영어로 작성합니다.
* 언어가 불명확하면 사용자에게 확인합니다.
* 사용자가 명시적으로 요청하지 않는 한 commit body는 작성하지 않습니다.

### 3. 커밋 전 확인

스테이징 대상 파일과 제안하는 커밋 메시지를 사용자에게 보여준 뒤 **승인을 기다립니다.**

다음과 같이 간결하게 제시합니다.

```text
스테이징 대상: <files>

커밋 메시지: <type>: <subject>
```

명시적인 승인 없이 커밋하지 않습니다.

### 4. 스테이징 및 커밋

사용자가 승인한 후 의도한 파일만 스테이징합니다.

```bash
git add <paths>
git commit -m "<type>: <subject>"
```

사용자가 요청하지 않는 한 무분별한 `git add -A`, `git add .`는 사용하지 않습니다.

### 5. 푸시

푸시는 원격 저장소에 변경사항을 게시하는 작업이므로 **항상 별도로 확인합니다.**

먼저 현재 브랜치와 원격을 확인합니다.

```bash
git rev-parse --abbrev-ref HEAD
git remote -v
```

사용자에게 다음 정보를 보여주고 확인받습니다.

```text
브랜치: <branch>
원격: origin

푸시할까요?
```

사용자가 승인한 후 다음 명령을 실행합니다.

```bash
git push origin <branch>
```

브랜치에 업스트림이 설정되지 않은 경우:

```bash
git push -u origin <branch>
```

## 하지 말아야 할 것

* `feat`, `fix`, `docs`, `chore`, `test` 외 커밋 타입을 사용하지 않습니다.
* `scope`를 사용하지 않습니다.
* `feat(step-1-setup): ...`과 같은 형식을 사용하지 않습니다.
* 명시적 요청 없이 장황한 여러 줄 메시지나 body를 작성하지 않습니다.
* subject에 긴 대시(`—`, `–`)를 사용하지 않습니다.
* subject에 가운데점(`·`)을 사용하지 않습니다.
* 여러 내용을 구분해야 할 경우 `-` 또는 `,`를 사용합니다.
* 무엇이 일어날지 보여주고 확인받지 않은 채로 커밋하지 않습니다.
* 푸시 역시 확인 없이 실행하지 않습니다.
* 사용자가 명시적으로 요청하고 결과를 이해하지 않는 한 force-push(`git push -f`)를 사용하지 않습니다.
* 히스토리를 임의로 재작성하지 않습니다.
* 게시된 커밋을 임의로 amend하지 않습니다.
* 작업 트리에 무관한 변경이 있을 때 무분별한 `git add -A` 또는 `git add .`를 사용하지 않습니다.
* 변경이 모호할 때 커밋 타입을 추측하지 않습니다.

## 응답 스타일

* 사용자가 한국어로 작성하면 한국어로 응답합니다.
* 간결하게 작성합니다.
* 명령어와 관련 출력 중심으로 보여줍니다.
* 모든 단계를 장황하게 설명하지 않습니다.
* 커밋 전에는 변경사항 요약, 스테이징 대상, 제안 메시지를 명확하게 보여줍니다.
* 커밋 후에는 커밋 결과를 간결하게 보여줍니다.
* 푸시 전에는 브랜치와 원격을 명확하게 보여주고 확인받습니다.
